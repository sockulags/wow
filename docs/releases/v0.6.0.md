# wow 0.6.0

One main thread runs the work: its agent starts helpers on Claude Code or Codex, helpers start
helpers of their own, every approval and question from the tree comes up in the main thread, and
a workflow is a Markdown file the agent follows. Calendar cards start such threads on a schedule.
The thread list is in front, and the pages this replaces are gone.

Built and reviewed by agents, run against mock agents and mock hosts only. Read "Known gaps" and
"Removed" before you update: the update deletes stored runs, plans, event triggers, briefings and
the decision queue.

## Changes

### Helpers

- **Helpers in depth.** A helper below **How deep helpers go** (`chat.helperDepth`, 2) can start
  helpers of its own, in any folder or Git repository it names, with or without its own copy (a
  branch `wow/helper/<id>`). Their answers come back to the thread that started them.
- **Stop** on a main thread stops its whole tree; Mark done is refused while a helper works.
- **`merge_helpers`** starts a merge helper in its own copy that merges the named helpers'
  branches, so you review one merged branch in that helper's Changes.
- `read_helper` tells the agent each helper's folder, repository, branch and commits ahead.

### Gates in the main thread

- Every approval and question for you from any helper in the tree shows as a card at the end of
  the main thread and is answered there. Only the asking helper waits.

### wow's tools in every main thread

- Every main thread's agent has the app tools the assistant had: settings, projects, trackers,
  workflows, calendar cards, the backlog and the readers of mail and calendar. Changes show as a
  row with Undo, and a change that lets wow do more on its own as a proposal with Yes and No,
  right after the call in that thread.
- A thread can have no project: it works in its own empty folder under wow's home.
- **Provider of a new thread** and **Model of a new thread** (`chat.defaultInstance`,
  `chat.defaultModel`).
- **Instructions for main threads** (`chat.instructions`) are told to every main thread after
  the provider's own instructions. A stored assistant instructions text moves here.
- **Assistant** is now a main thread like the others, without a project, with its conversation
  kept.

### Workflows as text

- A workflow is a Markdown file: every `<name>.md` in `<wow home>/workflows`, or in a project's
  `.wow/workflows` (the project's file wins on a name clash).
- **`/name text`** in the composer starts it in the thread; gates are question cards the agent
  asks for.
- Settings › Workflows lists the files, opens one in your editor and makes a new one from
  `workflows.newTemplate`.
- On first start the workflows stored in the database are written out once as files. A file that
  is already there is never overwritten; a clash gets `<name>-1.md`.

### Calendar cards start threads

- Each occurrence of a card with a workflow starts a main thread that runs the card's workflow
  file. **Each time it runs** picks a new thread each time (titled with the card and the day) or
  the card's one thread.
- The card follows its thread: running, waiting while it or a gate card in it waits for you, and
  done, failed or stopped by how the last turn ended. A backlog item planned on the card follows
  it too.
- A thread that cannot start fails the card or the occurrence with the reason.

### Threads in front

- wow opens on chat. The left side is the thread list of main threads, by status: **Waits for
  you** (an exclamation mark), **Working**, **Unread**, **Done**, pinned first, then the newest.
- One **Settings** button at the bottom of the list opens Calendar, Backlog, Workflows and
  Settings; Escape goes back to the thread. Their palette commands and keys stay.
- The list keeps the filter, project chips, pin, archive, mark done, the row menu and picking
  several rows.

## Removed

These are gone with their pages, routes, commands, keys and settings:

- **Plans** and plan runs, **workflow runs** with the run view, the workflow builder, and the
  **Runs** and **Triggers** tabs. Event triggers are gone; host reads no longer start anything.
- The **Assistant** page with its briefings, the **decision queue** (also in the tray), the
  assistant's **standing permissions** and the threads it started under them, and its **Memory**
  notes.
- **Threads at work**, **Usage** and **Quick ask** (with its global shortcut).
- The thread list's time groups, group by project and detailed second line.

What the update does with what you have (migrations 0048 to 0052):

- Stored workflows are kept as data and written out as files (see above).
- A workflow step's thread stays as a thread marked done. One that worked in its run's own copy
  moves to its project's folder and starts a new session there.
- A card or backlog item that waited on a run is freed: the card shows Stopped, the item Planned.
- Run history, plan runs, event triggers, briefings, the decision queue, standing permissions,
  the assistant's notes and the settings only they used are deleted. A thread the assistant
  started stays as an ordinary thread.
- Usage records and provider limits stay. Intent files in your repositories are not touched.

## Known gaps

- Nothing in this release has been run against a real Claude Code or Codex, a real GitHub or
  GitLab, a real Outlook, or on Windows outside CI.
- A Codex helper that starts helpers of its own carries the `wow` server with its own token; that
  it keeps your own `config.toml` servers beside it was seen against the mock only.
- The working copies of old workflow runs stay on disk under `workspaces.root` and in
  `git worktree list` until you remove them; nothing removes them any more.
- A setup file written by an older wow that names a removed setting is refused as a whole.
- A step thread whose project was removed keeps its old folder.
- Open: #49, #65, #66 (Windows only), #67, #69.
