# wow 0.2.0

Judge agent work at a gate without leaving wow, let workflows branch and run a plan's units on
their own, and set the app up by talking to an assistant that never sees a secret. The mail rail is
gone.

Everything here was built and reviewed by agents while the owner was away and has only been run
against mock agents and mock hosts. Read "Known gaps" before relying on it.

## Changes

### Review at a gate

- **Chat renders what the agent wrote:** tables, nested lists, code and `mermaid` diagrams.
- **Side panel:** a markdown file, picture, HTML page or text file a step produced opens beside the
  conversation.
- **Changes tab:** every file changed since the run started, as a diff, with the waiting step's
  files marked.
- **Approve or Send back:** a run waiting at a gate shows the conversation, the changes, the
  artifacts, the pull request, the ticket and linked pages in one place. Approve passes the gate;
  Send back runs the step again with your note. Both act inside wow only.
- **Pull requests, tickets and pages from your own hosts:** GitHub Enterprise, GitLab, Jira and
  Confluence, each through its standard API at the address you store, with a personal access
  token. wow only reads, and only what belongs to a live run or a plan you follow.

### Plans and automation

- **Plans:** the intents and units of a project with each unit's status (ready, claimed,
  delivered, blocked), read from the plan files and the pull requests.
- **Run ready units:** a workflow works through a followed plan one unit at a time, each in its
  own working copy (a Git worktree), so runs do not disturb the folder you work in.
- **Event triggers:** start a run when a pull request merges, checks fail or a review comment
  arrives. wow notices by asking the hosts on a timer; how often is a setting.
- **Gates that pass by themselves:** a gate after a step can pass on the step's verdict, green
  checks or expected artifacts. Which gates may do this is set per workflow.
- **Branches in workflows:** a step carries rules ("after this step"): go back to an earlier step,
  skip, end, or follow a rule when the step fails, with a limit on how often a step is visited.
  The builder draws every path; the run view shows the path taken. The default templates loop
  check-work back to deliver-work.

### Assistant

- **A new Assistant view:** say what you want and it changes settings, schedules cards and builds
  workflows. Every change is a row with Undo. Anything that changes what agents may do on their
  own, or could send a stored token somewhere new, waits for your yes.
- **It never sees a secret.** It shows where to make a token on your host, step by step, and puts
  a field beside the conversation that you fill in yourself. A message that looks like a token is
  held before it is sent.
- **It says what is failing** and where to fix it.
- **Setup file:** Settings → Advanced saves your setup to a YAML file without tokens, account
  names or machine paths. A colleague starts from it with a preview and one Undo.
- **First start:** a new install shows only "Connect an agent"; then the assistant greets and
  walks through what is missing.
- The assistant runs on Claude Code. On Codex it could run read-only shell commands and so read
  files that hold secrets, which wow cannot switch off; the setting "Let the assistant run on
  Codex" is off unless you turn it on.

### Removed

- **Mail.** The mail rail, its settings (`outlook.folders`, the key for the rail) and the mail wow
  had stored are removed when 0.2.0 first starts. Meetings still show.

### Fixed

- The server could stop on Windows while saving a secret, when another program had the secrets
  file open at that moment.

## Known gaps

- Nothing in this release has been run against a real Claude Code or Codex, a real GitHub
  Enterprise, GitLab, Jira or Confluence, a real Outlook, or on Windows outside CI.
- That a real Claude Code keeps the assistant to wow's own tools is tested only through the
  options wow sends, not against the program. Check section 10 of `docs/windows-smoke.md` first.
- A run started by a pull request event checks out the head branch by name; a fork's branch named
  like a local one gives the wrong code. Do not point event triggers at repositories that take
  pull requests from forks.
- When a rule runs a step again while its thread is answering a message you typed there, the run
  fails.
- After a loop, the Changes tab can mark a file for the wrong step, and a wait before a step that
  is visited again can show as a gate after it.
- Long Jira descriptions with many `[` or `{{` slow each poll down.
- The other open findings are listed in pull request #34.
